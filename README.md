# Compensation Intelligence System

A backend-focused MVP for structured, comparable compensation data — built for the
**Backend Engineer / Track B** internship assignment. The core principle: **levels
matter more than job titles.**

> **All compensation data in this project is synthetic/demo data**, generated by
> `apps/api/prisma/seed.ts`. It does not represent real salaries at any company named
> in the dataset. See `docs/research.md` for how competitor products were researched
> without scraping or copying their data.

## Tech Stack

| Layer | Choice |
|---|---|
| Backend | NestJS (TypeScript), REST, `/api/v1` |
| Database | PostgreSQL + Prisma ORM, `Decimal` for money |
| Frontend | Next.js (App Router) + React + TypeScript + TailwindCSS |
| API docs | Swagger/OpenAPI at `/api/docs` |
| Testing | Jest (unit) + Jest/Supertest (e2e, against a dedicated test database) |

See `docs/architecture.md`, `docs/data-model.md`, and `docs/decisions.md` for the
reasoning behind these choices.

## Prerequisites

- Node.js 20+
- A PostgreSQL 14+ server (either `docker compose up -d`, or a native/local install)

## Setup

```bash
npm install
```

### 1. Configure environment variables

```bash
cp .env.example apps/api/.env
```

Edit `apps/api/.env` and set `DATABASE_URL` to point at your Postgres instance, e.g.:

```env
DATABASE_URL=postgresql://<user>:<password>@localhost:5432/compensation_intelligence?schema=public
PORT=4000
NODE_ENV=development
CORS_ORIGIN=http://localhost:3000
```

For the frontend, create `apps/web/.env.local`:

```env
NEXT_PUBLIC_API_URL=http://localhost:4000/api/v1
```

### 2. Start PostgreSQL

Either:

```bash
docker compose up -d
```

or point `DATABASE_URL` at any Postgres server you already have running and create the
database (e.g. `createdb compensation_intelligence`).

### 3. Run migrations and seed synthetic data

Run these from the **repo root** (they already target `apps/api` internally — do not
add `--workspace=apps/api` yourself, that double-scopes it and npm won't find the
script):

```bash
npm run db:migrate   # applies prisma/migrations, generates client
npm run db:seed      # loads ~350 synthetic compensation records
```

The seed script targets 20+ companies, 12 roles, 100+ company-scoped levels, 14
locations, and ~350 compensation records spanning INR/USD/GBP/SGD/EUR, per the spec's
minimum data requirements.

### 4. Run the apps

Also from the repo root, in two separate terminals:

```bash
npm run dev:api   # http://localhost:4000/api/v1
npm run dev:web   # http://localhost:3000
```

API docs (Swagger): `http://localhost:4000/api/docs`
Health check: `http://localhost:4000/api/v1/health`

## API Endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/v1/compensation` | Ingest one compensation record |
| GET | `/api/v1/compensation` | Filter/sort/paginate compensation records |
| POST | `/api/v1/ingestion/compensation/bulk` | Bulk ingest with a per-record summary |
| GET | `/api/v1/companies` | List companies with record counts |
| GET | `/api/v1/companies/:slug` | Company detail: statistics (per currency), roles, levels, locations |
| GET | `/api/v1/analytics/overview` | Dashboard-level aggregate counts |
| GET | `/api/v1/compare` | Compare compensation statistics across companies (single currency, required) |
| GET | `/api/v1/health` | Liveness/readiness, including a live DB check |

Full request/response schemas: `/api/docs`.

## Data Quality

- **Validation**: every write goes through `class-validator` DTOs (`whitelist: true`,
  `forbidNonWhitelisted: true`) — required fields, non-negative monetary values, an
  explicit currency allowlist, and rejection of any client-supplied
  `totalCompensation`.
- **Normalization**: `NormalizationService` deterministically normalizes company/role/
  level/location text (trim, lowercase, punctuation/suffix stripping) — no fuzzy or
  AI-based matching. See `docs/decisions.md`.
- **Duplicate handling**: a SHA-256 fingerprint of normalized identity fields, enforced
  with both an application-level check (clean `409 Conflict`) and a database-level
  `UNIQUE` constraint. See `docs/data-model.md`.
- **Compensation calculation**: `totalCompensation = baseSalary + bonus + stock`,
  computed server-side with `Prisma.Decimal` (never floating point); missing
  bonus/stock default to `0`.

## Testing

```bash
npm run test:api   # from repo root — unit tests (normalization, calculation, duplicate detection)
cd apps/api && npx jest --config ./test/jest-e2e.json   # integration tests against a dedicated test DB
```

Before running e2e tests once, point a **separate** test database at
`apps/api/.env.test` and apply migrations to it:

```bash
cp apps/api/.env apps/api/.env.test   # then change DATABASE_URL's db name, e.g. ..._test
cd apps/api && DATABASE_URL="<your test db url>" npx prisma migrate deploy
```

e2e tests truncate this database between tests — never point `.env.test` at your seeded
dev database.

Current coverage: 25 unit tests (normalization, total-compensation calculation,
duplicate fingerprinting) and 16 integration tests (ingestion success/validation/
duplicate/bulk-summary, filtering/sorting/pagination limits, company detail 404 and
per-currency statistics, analytics overview, and compare's required-currency /
never-mixed-currency behavior).

## Deployment

- **API**: any Node host compatible with NestJS (Railway/Render fit well). Build with
  `npm run build --workspace=apps/api`, run `node apps/api/dist/main.js`, and run
  `npx prisma migrate deploy` against the production database before first boot.
- **Database**: Neon, Railway, or Render Postgres.
- **Frontend**: Vercel. Set `NEXT_PUBLIC_API_URL` to the deployed API's `/api/v1` URL,
  and set the API's `CORS_ORIGIN` to the deployed frontend's origin.

## Known Limitations

- No authentication — ingestion endpoints are open (rate-limited only). A real
  deployment accepting untrusted public writes would need an API key or auth layer in
  front of them first.
- No currency conversion — by design (see `docs/decisions.md`), not an oversight.
- Company name normalization is deterministic/rule-based, not fuzzy — genuinely
  different spellings/typos for the same company are not merged.
- Level `seniorityRank` is a manually-curated, coarse hint for cross-company sorting,
  not a verified equivalence.
- Seed data is synthetic and randomly generated within realistic bands; it is not
  derived from any real compensation data.

## Recommended Next Steps

- API-key or token auth in front of the ingestion endpoints.
- Company alias table for known name variants that don't reduce to the same normalized
  form (a real fuzzy-matching layer, added deliberately rather than by default).
- Historical trend view (compensation over time) once enough `reportedAt` spread
  exists in real submissions.
- A small chart on the company page (e.g. total-compensation distribution) — omitted
  from this MVP per the spec's "don't add charts merely for decoration" guidance, since
  the existing per-currency statistics already answer the "what does this look like"
  question numerically.
